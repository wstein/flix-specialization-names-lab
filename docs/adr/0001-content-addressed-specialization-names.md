# 1. Content-addressed names for specialized classes

## Status

Proposed

## Context

The Flix compiler generates one JVM class per specialization of a
polymorphic def, struct, or enum. Today that class name ends in a suffix
minted from a global, monotonically increasing counter (`$1234`). The
counter's value depends on how many fresh symbols were allocated before it,
so it renumbers whenever an unrelated declaration earlier in the compilation
order is added, removed, or reordered — even when the specialization itself
did not change.

Measurements on the compiler fork (`feat/stable-specialization-names-2`)
quantified this: across a perturbation of the standard library and a
representative source file, 96.5% of counter-derived specialization names
changed between two otherwise-equivalent builds. That churn breaks anything
that wants to compare generated bytecode or class names across builds —
diffing output, caching by class name, or correlating a name back to the
source declaration that produced it after an unrelated edit elsewhere in the
project.

## Decision

Replace the counter suffix with a content-addressed one: a SHA-256 hash of
the specialization's identity (its originating symbol plus its
instantiation, e.g. the resolved type arguments), rendered as a fixed-width,
13-character lowercase base-36 string. The suffix is a pure function of what
is being specialized, not of compilation order, so it is stable across
recompiles and changes only when the thing it names actually changes.

This lab exists to validate that decision independently of the compiler
fork: `src/hello.flix` is a demo written to exercise every id-bearing symbol
kind the compiler can mint, and `class-id-report.scala` censuses the
generated `.class` files after the fact, without invoking the compiler, to
tell counter-derived ids apart from hash-derived ones and measure how many
of each survive an unrelated edit.

### Why SHA-256 over XXH3-64 or another non-cryptographic hash

A faster hash such as XXH3-64 or FarmHash was the first thing considered,
since nothing here needs cryptographic properties — only a low collision
rate over a few million inputs. Two things ruled them out:

- **Algorithm permanence.** SHA-256 is a fixed, formally specified algorithm
  (FIPS 180-4): the same input has produced the same digest since 2001 and
  will keep doing so. XXH3 is not similarly frozen — it went through
  breaking output changes during its own development (pre-0.8.0 `xxhash`
  releases do not agree with later ones on the same input), and nothing
  prevents a future revision doing the same. A hash whose whole purpose is
  long-term stability cannot be built on an algorithm that has already
  changed its output once and carries no guarantee against doing so again.
- **No extra dependency.** `java.security.MessageDigest` ships in the JDK,
  so SHA-256 is available with zero added dependencies to the compiler.
  XXH3 and FarmHash both require pulling in a third-party library — one more
  thing to pin, update, and trust not to change its output between versions.

The speed difference is immaterial here: hashing a symbol's fully qualified
name and type arguments is not on any hot path that runs anywhere near often
enough for the choice of hash function to be measurable.

### Why base-36 over base-62

Base-62 packs more bits per character, giving a shorter suffix
for the same collision resistance. It was rejected here for a reason specific to this use
case: the suffix becomes part of a JVM class name, and a class name becomes
a `.class` file name on disk.

macOS's default filesystem (APFS, case-insensitive by default) and
Windows's (NTFS, case-insensitive) do not distinguish files whose names
differ only in case. A mixed-case suffix scheme can legally produce two
distinct class names — distinguishable to the JVM and on Linux's
case-sensitive filesystems — that collide into the same file on disk on
those two platforms, silently overwriting one specialization's `.class`
file with the other's. That failure mode would not show up in Linux CI and
would only surface for contributors and users on the two most common
desktop platforms.

Base-36 (`0-9a-z`, all lowercase) cannot produce this collision by
construction: there is only one case to render a digit in, so two different
hashes never differ by case alone. The cost is a longer, fixed-width
13-character suffix instead of a shorter mixed-case one, which is accepted
in exchange for not having a platform-specific failure mode.

## Consequences

- Specialization names become stable across recompiles that do not touch the
  specialized code itself, at the cost of losing the (already meaningless to
  humans) ordering information a counter incidentally encoded.
- Names get longer and case-insensitive-collision-safe (13 base-36 characters
  versus a variable-length decimal counter), which is a larger, fixed
  footprint per generated class name.
- Anything that parsed or pattern-matched the old `$<digits>` suffix format
  needs to accept `$<13 lowercase alphanumeric characters>` as well; the two
  are told apart by the fact that a counter suffix is never exactly 13
  characters when read as a decimal number and a hash suffix is always
  exactly 13 base-36 characters.
- The hash must be computed from something that is itself stable — the
  originating symbol's fully qualified name and the specialization's
  resolved type arguments — rather than from anything positional, or the
  scheme degenerates back into the problem it fixes.
